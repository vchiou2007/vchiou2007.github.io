100 位並行使用者 SLA 驗證：從腳本設計到正式報告。

這是一個完整的效能工程實作案例：已知 SLA 條件後，如何把它轉成可執行的 LoadRunner 測試設計。 重點不只是把 Vuser 設成 100，而是建立正確的業務比例、交易模型、pacing、monitoring、 steady-state 分析與專業報告。

SLA Translation

第一步：把 SLA 轉成可測試條件

資深效能工程師不會一開始就打開 Controller 隨便放 100 users，而是先把 SLA 拆成明確的測試目標與判斷條件。

SLA 項目 測試標準 工程意義
並行使用者 100 concurrent active users 必須在 peak-hour 模型下穩定維持 100 位活躍使用者。
Login 95th percentile <= 3 sec 不是看平均值，而是 95% 的登入交易要在 3 秒內完成。
Search 95th percentile <= 2 sec Search 通常是讀取壓力與資料庫查詢瓶頸的重要指標。
Submit Order 95th percentile <= 5 sec 驗證下單流程、DB write、inventory、payment 或 order service 的承載能力。
Error / Throughput / CPU Error <= 1%, hits/sec >= 20, CPU <= 80% 同時看交易成功率、流量是否達標，以及 server 是否進入資源瓶頸。
End-to-End Design

完整流程：從腳本到報告

這個案例的專業重點，是把 SLA 變成可重複執行、可監控、可判斷、可交付給團隊的測試流程。

01

建立 workload model，而不是只設定 100 users

將 100 位使用者拆成合理業務比例：Search_User 70、Buyer_User 20、Login_User 10。這比所有人同時下單更接近一般 peak-hour 行為。

02

設計三種 VUGen 腳本與交易

Search_User 包含 Login 與 Search；Buyer_User 包含 Login、Search、Submit_Order；Login_User 持續 Login/Logout，確保 steady state 期間仍有登入樣本。

03

設定 think time、pacing 與資料驅動

Search 使用 3-5 秒 think time，Buyer 使用 5-8 秒，並依照 hits/sec 目標調整 pacing。100 users 要達到 20 hits/sec，平均每位使用者約 5 秒產生 1 hit。

04

在 Controller 建立正式場景

Manual Scenario：10 分鐘 ramp-up 到 100 users，維持 30 分鐘 steady state，再用約 5 分鐘 ramp-down。正式 SLA 只用第 10 到第 40 分鐘判斷。

05

測試前先接好 Web/App/DB/APM 監控

正式測試前要先連接 CPU、memory、disk I/O、network、thread pool、connection pool、DB active sessions、lock waits、slow SQL 與 APM service metrics。

06

先做 dry run，再做正式 SLA test

先跑 1-user smoke test、5-10-user shakeout test、50-user trial run，確認 correlation、test data、monitoring、load generator 能力與腳本穩定性。

07

正式測試後只分析 steady-state

排除 ramp-up、ramp-down、初始化與 cache warming，只用 30 分鐘穩定負載區間判斷 Login/Search/Submit_Order、error rate、hits/sec 與 CPU。

Scenario Setup

Controller 場景設計

這個設定讓測試符合 SLA 需求，也避免把 ramp-up 或 ramp-down 的不穩定資料拿來誤判系統能力。

項目 建議設定 原因
Scenario Type Manual Scenario 可精準控制每個 user group、ramp-up、steady state 與 ramp-down。
User Mix Search 70 / Buyer 20 / Login 10 模擬 peak hour 中搜尋、購買與登入活動的合理混合。
Ramp-up 每分鐘增加 10 users，10 分鐘到 100 users 避免瞬間啟動造成非業務型衝擊，也方便觀察瓶頸何時出現。
Steady State 100 users 維持至少 30 分鐘 這是 SLA 的正式驗證期間。
Ramp-down 每 30 秒停止 10 users，約 5 分鐘結束 平順結束測試，避免資料與系統狀態突然中斷。
Logging 正式測試只開 errors only 避免 extended log 讓 load generator 自己成為瓶頸。
Monitoring Strategy

監控要在測試前接好

如果測試前沒有連接監控，測試後 Analysis 不會憑空產生 CPU、DB、thread pool 或 slow query 資料。

Web / App Server

基礎設施與應用資源

CPU、memory、disk I/O、network I/O、process CPU、thread count、connection count。這些指標可以判斷是否是主機、process 或連線資源造成瓶頸。

Database

資料庫與查詢壓力

DB CPU、active sessions、lock waits、query response time、connection pool usage、disk read/write latency。這些指標用來確認是否是 DB 查詢或鎖定造成交易變慢。

APM

服務層與根因分析

若有 Dynatrace、AppDynamics、Datadog 或 New Relic，應觀察 service response time、failure rate、DB calls、external calls、GC、thread pool 與 connection pool。

Load Generator

測試工具本身也要監控

如果 load generator CPU 過高、logging 過多、test data 不足或 correlation 錯誤，測試結果可能是測試設計問題，而不是系統真的不行。

Pass / Fail Logic

如何判斷通過或失敗

正式判斷只看 30 分鐘 steady state。任何重要 SLA 未達標，都不能算完整通過；但失敗後要先做 root cause，而不是直接怪開發團隊。

Performance Engineer Issue

測試設計問題

Vusers 沒穩定到 100、script correlation 錯誤、think time/pacing 錯、test data 不足、load generator 過載、monitor 未接好、把 ramp-up 算進 SLA，這些應先修正測試設計後重跑。

Dev / DBA / Infra Issue

系統瓶頸問題

Search API 慢、Submit Order timeout、DB slow query、CPU 長時間高於 90%、connection pool 滿、thread pool 滿、lock wait 高、GC pause 嚴重或 500 errors 超標，應帶證據交給對應團隊。

在 100 concurrent active users 與 30 分鐘 steady state 條件下，報告摘要會直接指出超標的 transaction、95th percentile 與 SLA 目標的差距、APM 顯示的主要耗時來源，以及後續應由 DBA、開發或基礎架構團隊處理的具體方向。
Executive Summary

SLA 驗證摘要

以下是本次 LoadRunner SLA 驗證結果的中文與英文摘要。

中文摘要

在 100 位並行活躍使用者與 30 分鐘 steady-state 驗證期間，Search transaction 的 95th percentile response time 為 3.8 秒，超過 SLA 目標 2 秒。

Dynatrace 顯示，Search API 的資料庫呼叫佔整體 response time 的 78%。ProductSearch SQL 平均耗時 2.6 秒，資料庫 CPU 最高達到 87%。

建議由 DBA 與開發團隊優先檢查 ProductSearch SQL 的 query plan、索引設計、connection pool 設定，以及是否需要加入或調整快取策略。

English Summary

Under 100 concurrent active users and a 30-minute steady-state validation window, the Search transaction reached a 95th percentile response time of 3.8 seconds, exceeding the SLA target of 2 seconds.

Dynatrace indicates that the database call within the Search API accounts for 78% of the total response time. The ProductSearch SQL averaged 2.6 seconds, and database CPU peaked at 87%.

The DBA and development teams should prioritize reviewing the ProductSearch SQL query plan, index design, connection pool configuration, and potential cache strategy improvements.
